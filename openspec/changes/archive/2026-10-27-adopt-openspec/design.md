# Design

## Context

- The repository never used Agent OS or OpenSpec. It has a flat root module (`versions.tf`, `variables.tf`, `data.tf`, `locals.tf`, `main.tf`, `outputs.tf`), two examples (`examples/minimal`, `examples/complete`), no `tests/` directory and a `CHANGELOG.md` generated by git-cliff.
- The reference modules are `keycloak`, `vault` and `gitlab-management`: same stores, same `AGENTS.md` / `CLAUDE.md` shape, `scripts/openspec-setup.sh`, `.gitlab/specs.yml` and `spec-validate` / `spec-setup` mise tasks.
- The stores `quality`, `repository` and `terraform` are pinned by tag in `openspec/config.yaml` (copied from the `terraform-module` profile).

## Goals / Non-Goals

**Goals:**
- One planning system (OpenSpec), standards consumed by pinned reference, never copied.
- A baseline of the current contract that later changes modify with deltas.
- Zero diff in `.tf` files, so this change cannot break a consumer.

**Non-Goals:**
- Applying the store standards to the code (for example marking password inputs sensitive, adding `tests/main.tftest.hcl`, `check` blocks). Specs written here describe today's behaviour, even where a standard would later ask for more.
- Changing how `CHANGELOG.md` is produced.

## Decisions

### 1. Bootstrap the baseline through this change
The specs are ADDED deltas here and land in `openspec/specs/` on archive, so they are reviewed and `validate --strict`-checked like any other change.

### 2. Baseline describes today's behaviour
Alternative: write the target contract. Rejected: specs would disagree with the code until a later change fixes it. Observed oddities are left out of the specs or described as they behave and reported in the change review.

### 3. Four capabilities
`module-contract` (versions, inputs, outputs), `ssh-keys`, `servers` (lookups, expansion, credentials, options, networks, timeouts) and `flexible-ips`. The module is small and one resource family maps to one capability; offer and OS lookups are only meaningful for servers, so they live there. No `check` block exists, so no guardrails capability is created.

### 4. Skills for Claude Code and OpenCode
Both skill sets are installed and identical; OpenCode reads `AGENTS.md` natively and Claude Code reads it through `CLAUDE.md`.

### 5. CI job `validate:specs`
`.gitlab/specs.yml` runs `openspec validate --all --strict` with the CLI version in `OPENSPEC_VERSION` (same pin as `mise.toml`). No store is needed in CI.

### 6. CHANGELOG stays generated by git-cliff
`CHANGELOG.md` is built from commit subjects (`mise run changelog`, `.cliff.toml`); the OpenSpec rules therefore ask for commit subjects that read as changelog lines instead of a hand-edited `## [Unreleased]` section.
