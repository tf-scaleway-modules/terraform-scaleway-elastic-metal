# Proposal

## Why

This module has never had a planning system: no Agent OS, no OpenSpec specs, only the code, the README and a git-cliff generated `CHANGELOG.md`. The sibling modules (`keycloak`, `vault`, `gitlab-management`) already plan changes with OpenSpec and consume the pinned `quality`, `repository` and `terraform` stores. Adopting OpenSpec here gives the module the same workflow and, above all, a baseline contract that future changes (for example hardening the installation password inputs) can modify with delta specs.

## What Changes

- First adoption of OpenSpec: configure `openspec/config.yaml` (stores `quality`, `repository`, `terraform` pinned by tag, module `context`, per-artifact `rules` and `operations` guidance) and add `AGENTS.md` plus `CLAUDE.md`.
- Install the `openspec-*` skills for Claude Code (`.claude/skills/`) and OpenCode (`.opencode/skills/`).
- Write the baseline capability specs under `openspec/specs/`, describing the module **as released today** (including the write-only installation passwords added with the provider `~> 2.86` upgrade).
- Tooling: pin `node` and `openspec` in `mise.toml`, add `spec-validate` and `spec-setup` tasks, add `scripts/openspec-setup.sh`, and validate specs in CI through `.gitlab/specs.yml` (`validate:specs`).
- README "Contributing" section: pointer to the OpenSpec workflow.
- No change to any `.tf` file, input, output or resource: semver **patch**, no consumer impact. `CHANGELOG.md` stays generated by git-cliff.

## Capabilities

### New Capabilities
- `module-contract`: Terraform/OpenTofu and provider constraints, no provider/backend blocks, every input with type, default and validation, every output and its sensitivity.
- `ssh-keys`: SSH keys created by the module and the SSH keys attached to servers.
- `servers`: offer and OS lookups, server definitions, `count` expansion, naming, tags, installation credentials (plain and write-only), options, private networks and timeouts.
- `flexible-ips`: flexible IPs attached to servers.
